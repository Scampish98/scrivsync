# Работа над scrivsync

## Назначение и интерфейс

- Это Go-программа для ручного обмена проектами Scrivener через ZIP на Яндекс Диске.
- Команды: `scrivsync push`, `scrivsync pull` и `scrivsync pull --force`. Пути и токен не передаются аргументами
  и не читаются из переменных окружения.
- Общайтесь с пользователем по-русски; сообщения CLI и основная документация также на русском.

## Конфигурация и структура

- Личные настройки: `configs/config.yaml`; пример для Git: `configs/config.example.yaml`.
- Исполняемый файл размещается в корне репозитория или в `bin/`. В обоих случаях
  программа ищет `configs/config.yaml` в корне, независимо от текущей папки запуска.
- Относительный `local_path` отсчитывается от `configs/`.
- `cmd/scrivsync/` — точка входа CLI. Сборка: `go build -o bin/scrivsync ./cmd/scrivsync`.
- `internal/config/` — конфиг; `internal/archive/` — ZIP и сравнение файлов;
  `internal/sync/` — отдельные `push.go`, `pull.go` и журнал восстановления;
  `internal/yandex/` — HTTP-клиент, передача и метаданные.
- `internal/scrivx/` — сравнение XML основного файла и отдельные списки правил в `rules.go`.
- `internal/report/` — сохранение диагностики и построчных диффов при конфликтах pull.
- `internal/lock/` содержит блокировки и проверку Scrivener для каждой платформы.
- `internal/fileutil/` — закрытие, очистка и fsync; `internal/ctxio/` — отмена чтения и ожидания.
- Не теряйте ошибки закрытия и очистки: возвращайте их, если это влияет на результат,
  иначе логируйте через `log/slog`. Не закрывайте ресурс дважды.
- `bin/`, `.idea/`, `vendor/`, личный конфиг и служебные данные обмена не коммитятся.
  Зависимости фиксируются в `go.mod` и `go.sum`.

## Правила сохранности данных

- Не выводите и не коммитьте токен, содержимое личного конфига или подписанные URL.
  В конфиге-примере поле `token` должно оставаться пустым.
- Перед изменением файлов проверяйте, что Scrivener закрыт. Не тестируйте на настоящем
  проекте или аккаунте Яндекс Диска без явного указания пользователя.
- Push сначала загружает и проверяет временный архив, затем переносит старый в
  `Backups` и устанавливает новый. Имя бэкапа содержит время создания старого
  облачного архива в UTC, без дополнительного идентификатора.
- Совпадение имени бэкапа — ошибка; перезапись запрещена. Старые бэкапы автоматически
  не удаляются. Уникальные идентификаторы допустимы у технических временных файлов.
- Pull проверяет все файлы до замены проекта. Постоянный полный локальный бэкап
  сохраняется только при принудительном принятии блокирующих конфликтов. При отсутствии
  блокирующих конфликтов старая
  папка временно хранится в `run-.../previous-project/` до успешной установки, затем
  удаляется вместе с рабочей папкой операции. До завершения установки её нельзя
  удалять: журнал использует её для восстановления. Постоянные бэкапы из старых
  журналов сохраняются после восстановления.
  Одинаковое содержимое не конфликтует независимо от дат. При разном содержимом
  архивный файл принимается только если он новее локального более чем на две секунды.
  Файлы только на локальной стороне и смена типа файл/папка считаются конфликтами.
- Исключения из блокирующих конфликтов заданы в `internal/archive/exclusions.go`
  отдельными списками `Files` и `Dirs`. Обрабатывайте их универсально; не добавляйте
  проверки конкретных имён в алгоритм. `Files` — точные пути, `Dirs` — всё поддерево,
  пути с `/` относительно проекта, папки без завершающего `/`, регистр учитывается.
  Смена типа файл/папка всегда блокирует. Локальный родитель с только исключёнными
  потомками не блокирует; пустые папки вне `Dirs` проверяются как обычно.
  Исключения остаются в ZIP, проверках целостности и отчёте.
  `Files/writing.history`, `.styles`, основная структура проекта и настройки
  компиляции не исключаются из конфликтов.
- Перед установкой при наличии конфликтующих исключённых файлов сохраняйте только
  их локальные версии в `FileBackups/<проект>_<время UTC>/`, с исходными путями и датами.
  Используйте те же правила конфликта: файл только локально либо разное содержимое,
  когда архив не новее более чем на две секунды. Одинаковые файлы и более свежие
  архивные файлы не требуют бэкапа. При блокирующем конфликте без `--force` проект
  остаётся нетронутым, отдельный бэкап не создаётся. Полный бэкап при `--force` уже
  содержит исключённые файлы; не дублируйте его выборочным бэкапом.
  Журнал фиксирует путь и снимок выборочного бэкапа. До установки проверьте копию,
  при ошибке остановитесь и оставьте прежний проект для восстановления. Частичную
  временную копию можно пересоздать, готовый постоянный бэкап перезаписывать нельзя.
- Для единственного корневого `.scrivx` сравнивайте значимое XML-содержимое; исходные
  байты не переписывайте. Правила путей/атрибутов находятся в `internal/scrivx/rules.go`.
  Неизвестные поля, порядок и структура Binder, названия и статистика остаются значимыми.
  Даты сеанса игнорируются точечно, счётчики и цели — нет. Ошибка разбора, неизвестный
  формат, отсутствие применимой базы возвращают обычные правила; совпадение значимого
  XML можно принять и без базы. Разные идентификаторы проектов всегда конфликтуют.
- База `baseline/project.scrivx` и `baseline/meta.json` берётся из переданного ZIP,
  а не из текущей рабочей папки. После успешной публикации/установки обновляйте её
  до завершения журнала; поддерживайте восстановление между переименованиями базы.
  Отправка ранее подготовленного снимка не должна записывать в базу последующие правки.
  Смена облачного пути/ID проекта и повреждённая база не разрешают конфликты автоматически.
  При неизменном локальном значимом XML принимайте архив; при локальных значимых
  изменениях и отличающемся архиве блокируйте pull независимо от дат. Пропущенный
  обычный конфликт `.scrivx` требует выборочного бэкапа. Полное совпадение файлов
  также обновляет базу, но не заменяет проект. Старые журналы должны восстанавливаться.
- `pull --force` принимает конфликты только после успешного создания отчёта;
  при наличии конфликтов полный бэкап обязателен перед заменой существующего проекта. Ошибка бэкапа или
  занятое имя останавливают замену. Проверки целостности, закрытого Scrivener и
  неизменности данных не отключаются. Журнал сохраняет необходимость оставить отчёт
  и скачанный ZIP после установки, включая восстановление после сбоя.
- При конфликте pull сохраняйте ZIP, распакованную копию и отчёт в отдельном `run-...`.
  Сбой создания отчёта не должен удалять скачанные данные. Без `--force` диагностика не создаёт
  журнал установки и не меняет решение о конфликте. RTF-дифф не считается смысловым
  сравнением текста и не разрешает автоматически перезапись.
- Сохраняйте восстановление через журнал при сбоях между перемещениями. Не удаляйте
  незавершённые журналы, снимки и бэкапы ради успешного повторного запуска.
- Проверяйте пути ZIP, контрольные суммы и ограничения распаковки. Ссылки и
  неподдерживаемые специальные файлы не должны попадать в проект.

## Проверка изменений

- Нужен Go 1.26 или новее. Форматируйте изменённые Go-файлы через `gofmt`.
- Для изменений программы выполните `go test ./...` и `go vet ./...`.
- Если меняются платформенные части или поиск конфигурации, проверьте сборки
  macOS arm64 и Windows amd64. Компиляция Windows не означает проверку запуска на Windows.
- Тесты должны использовать временные проекты и поддельный Disk/HTTP transport,
  не настоящий Яндекс Диск. Изменение README или .gitignore не требует новых тестов.
- Если локальный `vendor/` остался от старой сборки, проверьте также работу без него
  через `-mod=readonly`: в чистом клоне этой папки нет.
- После изменения интерфейса, путей или поведения обновляйте README и пример конфига.
